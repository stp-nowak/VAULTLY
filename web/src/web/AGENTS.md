# React App Agent Skill

> Part of the web app (`../../AGENTS.md`). The SPA holds **no tokens**: it calls only same-origin `/api/*`
> through `fetchJson` (`shared/api`), which sends the session cookie and the `X-CSRF: 1` header.

## Stack
- **React 19** + **TypeScript** (strict mode)
- **Vite** (bundler + dev server)
- **TanStack Router** (file-based routing)
- `pnpm` as package managing
- Tailwind CSS v4 + shared design system `@vaultly/ui` (`packages/ui`), consumed through the root pnpm workspace

## Architecture: Feature-Sliced Design (with `domain` instead of `entities`)

The frontend follows [Feature-Sliced Design](https://feature-sliced.design). The only deviation from
standard FSD: the `entities` layer is called **`domain`**, so the frontend speaks the same language as the
DDD backend (`./backend`) and the auth service (`./auth`). A `domain` slice maps to a backend
**bounded context** (e.g. `identity`, `transaction`, `budget`) and holds the frontend model of its aggregates.

```
src/
├── app/                      # App layer: init, providers, routing, global styles
│   ├── main.tsx              # Vite entry point
│   ├── App.tsx               # Providers composition (QueryClient, AuthProvider, Router)
│   ├── router.tsx            # Router instance + AppRouterContext
│   ├── routes/               # TanStack Router file routes (thin: guards, loaders, search params → page)
│   ├── routeTree.gen.ts      # Generated by the router plugin, never edit
│   ├── providers/            # Provider configs (queryClient.ts, ...)
│   ├── layouts/              # Root layout
│   └── styles/               # Global styles
├── pages/                    # One slice per screen; composes widgets/features/domain
│   └── [page]/
│       ├── ui/
│       └── index.ts          # Public API
├── widgets/                  # Large self-contained UI blocks (app shell, sidebars, dashboards)
│   └── [widget]/ui, model, index.ts
├── features/                 # User actions that bring business value (login, logout, add-transaction)
│   └── [feature]/ui, model, api, lib, index.ts
├── domain/                   # (FSD "entities") Business model per bounded context, mirrors backend DDD
│   └── [context]/            # e.g. identity  ↔  auth/ Identity service
│       ├── model/            # Types, state/context, selectors (aggregates & value-like types)
│       ├── api/              # API client, response parsers, TanStack Query options/hooks
│       ├── lib/              # Pure domain helpers
│       ├── ui/               # Display components of the domain (cards, badges, lists)
│       └── index.ts          # Public API
└── shared/                   # Business-agnostic code, no slices — only segments
    ├── api/                  # HTTP client (fetchJson, HttpError)
    ├── config/               # Env/app configuration
    ├── lib/                  # Generic helpers (readLocalPath, navigateToUrl for leaving the SPA)
    └── test/                 # Test utilities, MSW handlers/server
```

### Layer rules (enforced by ESLint `no-restricted-imports` in `eslint.config.js`)

Layers, highest to lowest: `app → pages → widgets → features → domain → shared`.

- A module may import **only from layers strictly below** its own (`app` may use everything, `shared` nothing).
- **Slices on the same layer must not import each other** (`features/login` cannot import `features/logout`).
  Move shared code down a layer (usually to `domain` or `shared`).
- Import other slices **only through their public API**: `@/domain/identity`, never `@/domain/identity/model/...`.
- Inside a slice use **relative imports**; across slices/layers use the `@/` alias.
- `shared` and `app` have no slices — import their segments directly (`@/shared/api`, `@/shared/test`); primitive UI comes from `@vaultly/ui`.
- If a `domain` slice genuinely needs another one (e.g. `budget` references `transaction`), use the FSD
  cross-import notation `domain/transaction/@x/budget.ts` instead of a deep import.

### Where does code go?

| Code | Place |
|---|---|
| Route definition, guards, loaders, search param validation | `app/routes/*.tsx` (render a page from `pages/`) |
| Screen composition | `pages/[page]` |
| Reusable composite block used by several pages | `widgets/[widget]` |
| An interaction/use case (form, button + mutation, flow) | `features/[feature]` |
| Types, state, API client and queries of a business concept | `domain/[context]` |
| Generic UI, HTTP, config, test helpers | `shared/[segment]` |

### Domain ↔ backend mapping

- One `domain/[context]` slice per backend bounded context (service). Keep names aligned:
  `domain/identity` ↔ `auth/` (Identity service), `domain/transaction` ↔ Transaction service, etc.
- Use the backend's ubiquitous language in type and function names (`Session`, `Budget`, `Goal`).
- Commands of the backend (write side) are triggered from `features`; queries (read side) are exposed as
  TanStack Query options/hooks from `domain/[context]/api`.
- Never model a backend aggregate twice — if two features need it, it belongs in `domain`.

### No circular dependencies

`src/app/circularDependencies/circularDependencies.test.ts` runs madge from `app/App.tsx` (aliases resolved via
`tsconfig.app.json`) and fails on any import cycle. Fix cycles by moving shared code down a layer, never by
disabling the test. `pnpm --filter @vaultly/web deps:circular` writes a JSON report next to the test.

> **Rule**: Keep code close to where it's used. Only move it down a layer when another slice truly needs it.

## TypeScript

- Always use `strict: true` in `tsconfig.json`
- Prefer `interface` for object shapes, `type` for unions/intersections
- Never use `any` — use `unknown` + type guards when type is truly unknown
- Define API response types in the owning slice (`domain/[context]/model/types.ts`); generic HTTP types in `shared/api`
- Use `satisfies` operator to validate objects against types without widening
- Export types separately from values (`export type { Foo }`)

## Component Patterns

- **Default**: functional components with explicit return types
- One component per file; filename = component name (PascalCase)
- **No `if`/early-return chains that render JSX.** Derive one state value in a pure, tested function (prefer lookup
  maps such as `Record<QueryStatus, Notice>` over `if` chains), map it to a small view model at a single branch point
  (e.g. `{ heading, body }`) and render shared markup once. Never repeat the same element (heading, wrapper) per state.
- **Conditional JSX elements use `&&`:** `{condition && <X />}` instead of `{condition ? <X /> : null}`; two branches
  spanning several lines as `{condition && (…)}{!condition && (…)}` instead of `{condition ? (…) : (…)}`. A two-branch
  ternary that fits on one line may stay. Keep `condition` a boolean (`items.length > 0 &&`, not `items.length &&`,
  which renders `0`). Ternaries that compute values (text, `className`, props, view models) are not affected.
- Keep components small and focused — extract logic into custom hooks
- Use **composition over configuration** — prefer `children` and slot patterns over large prop APIs
- Avoid prop drilling beyond 2 levels — lift to context or a store

```tsx
// Good
interface Props {
  title: string;
  children: React.ReactNode;
}

export function Card({ title, children }: Props) {
  return (
    <div>
      <h2>{title}</h2>
      {children}
    </div>
  );
}
```

## Performance

- **Code-split** routes automatically via TanStack Router's lazy loading
- **Lazy load** heavy components with `React.lazy` + `Suspense`
- Use `useMemo` / `useCallback` **only when profiling shows a problem** — don't pre-optimize
- Virtualize long lists (`@tanstack/react-virtual`)
- Keep state as local as possible — global state is a last resort
- Avoid anonymous functions and object literals in JSX props on hot render paths
- Use `React.memo` for pure components that receive stable props and re-render often

## State Management

| Scope | Tool |
|---|---|
| Local UI state | `useState` / `useReducer` |
| Server/async state | TanStack Query |
| Global client state | Redux Toolkit (or React Context for simple cases) |
| URL state | TanStack Router search params |

- Do **not** sync server data into client state — let TanStack Query own it
- Derive state instead of duplicating it
- Use **Redux Toolkit (RTK)** — never plain Redux
  - Define state in `createSlice`, scoped per slice (`src/domain/[context]/model/slice.ts` or `src/features/[feature]/model/slice.ts`)
  - Use `createSelector` for memoized derived state
  - Avoid non-serializable values (class instances, functions) in the store
  - Don't use RTK Query if TanStack Query is already in the stack — pick one

## TanStack Router

- Use **file-based routing** (`src/app/routes/`); route files stay thin and render a page from `src/pages/`
- Define loaders for data fetching at the route level (avoids waterfall)
- Use **search params** for shareable UI state (filters, pagination)
- Protect private routes with `beforeLoad` guards; a guard sends a visitor without a session to the landing page
  (`/?returnUrl=…`), never straight to sign-in
- Test guards and redirects through the real route tree with `renderApp` (`src/app/test`); leaving the SPA goes
  through `navigateToUrl` (`shared/lib`) so tests can mock it
- Always define route params and search params with TypeScript via `Route.createFileRoute()`
- When a route owns server data, preload it into TanStack Query in the loader instead of fetching the same resource twice

```tsx
// src/app/routes/users/$userId.tsx
export const Route = createFileRoute('/users/$userId')({
  loader: ({ params }) => fetchUser(params.userId),
  component: UserPage,
});
```

## Data Fetching

- Use **TanStack Query** for all server state
- Define query keys and `queryOptions` in the owning domain slice (`src/domain/[context]/api/`)
- Mutations live in the feature that triggers them (`src/features/[feature]/api/`)
- For route-owned data, prefer loader-driven prefetch + Query cache hydration over duplicate component-level requests
- Handle loading, error, and empty states explicitly in every data-dependent component

---

## Error Handling

- Wrap route trees and feature boundaries in `ErrorBoundary` components
- TanStack Router supports `errorComponent` per route — use it
- Never swallow errors silently; always log or surface them

## Styling

- **Tailwind CSS v4 only** — no Sass, no CSS modules, no other CSS libraries. Global CSS is just
  `app/styles/index.css` (`@import 'tailwindcss'; @import '@vaultly/ui/styles.css';`).
- Colors, fonts, shadows and base styles come from the shared design system **`@vaultly/ui`** (`packages/ui`).
  Use its tokens (`bg-canvas`, `text-muted`, `border-line`, `text-accent`, `font-display`, `shadow-panel`, …);
  never hard-code hex values or redefine tokens in the app. Need a new token? Add it to `packages/ui/src/styles.css`.
- Primitive UI (`BrandMark`, `Button`, `Card`, `Eyebrow`, `InfoTile`, `StatusNotice`, `CenteredScreen`) is imported from
  `@vaultly/ui` — do not recreate primitives in `shared/ui`. A primitive needed by more than one app belongs in the package.
- Compose conditional classes with `cn` from `@vaultly/ui` (clsx + tailwind-merge; later classes win).
- Avoid inline styles except for truly dynamic values; prefer arbitrary values (`max-w-[42rem]`) sparingly.
- User-facing copy only: no implementation details (tokens, cookies, APIs, issue numbers) in the UI.
